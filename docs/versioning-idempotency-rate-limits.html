API Versioning, Idempotency-Key & Rate Limiting (2026)

Resilient APIs survive client retries, traffic spikes, and version migrations without double-charging users or breaking integrations.

1. Idempotency-Key on POST Mutations (ADP-012)

Clients pass a UUIDv4/v7 in Idempotency-Key. The server caches the response keyed by (tenant, method, path, key) + request payload hash for 24h+, replaying the original 201 Created on network retries and returning 409 Conflict if the payload differs.

POST /v1/orders HTTP/1.1
Idempotency-Key: 019334b2-7d3a-7b8e-91c2-4a8e2e6f1100

2. IETF RateLimit Headers & 429 Backoff (ADP-013)

Return 429 Too Many Requests with Retry-After (seconds) and standard RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset headers.

HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 15
RateLimit-Limit: 120
RateLimit-Remaining: 0
RateLimit-Reset: 15

3. Explicit Versioning & RFC 8594 Sunset Headers (ADP-004, ADP-018)

Keep minor releases strictly additive (ADP-027). When retiring a major version, expose Deprecation and Sunset headers plus a Link: <...>; rel="successor-version".
